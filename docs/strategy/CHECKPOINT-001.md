# Strategic Checkpoint 001 — From Project OS to Steve 2.0

- **Date:** 2026-09-15
- **Project OS version:** v0.1
- **Framework state:** FROZEN
- **Experiments completed:** 2
- **Purpose:** Strategic checkpoint following Experiments 001 and 002

## Why This Checkpoint Exists

Project OS v0.1 has now been exercised against two materially different
projects:

1. LaunchCity — greenfield development
2. Lastman — adoption into an existing active project

Both experiments produced useful evidence.

Before running another experiment, this checkpoint records what has actually
been demonstrated, what appears to be emerging, and the broader direction
that Project OS may eventually support.

This document does not modify Project OS v0.1.

It is not a v0.2 specification.

---

# 1. North Star

Project OS is evolving toward the operating system for a personal AI-native
product and software development environment: **Steve 2.0**.

The intended system should allow a project to begin from:

- a new idea or blank page
- an existing Steve project
- an inherited external project or product

The objective is to start each project materially ahead of zero by drawing
on accumulated knowledge, precedent, preferences, decisions, reusable
patterns and previous evidence.

Project OS should then guide the project forward in a controlled and
proportionate way.

The intended outcome is not simply more code or more finished applications.

The system should help determine:

- what is worth exploring
- what problem is actually being solved
- what already exists and can be reused
- what should be prototyped
- what should become an MVP
- what deserves production investment
- what is too complicated
- what is too feature-light
- why something is not being used
- why something has failed
- what should be changed
- what should be productised
- what could have wider or commercial value
- what should be stopped

A prototype, MVP, production application, reusable capability, commercial
opportunity, pivot or deliberate decision to stop can all be successful
outcomes.

The common objective is proportionate effort applied to discovering and
delivering meaningful value.

---

# 2. Compounding Advantage

A core ambition of Steve 2.0 is that every project should make subsequent
projects cheaper, faster and better.

Today, new projects repeatedly pay a significant zero-to-project cost:

- product framing
- architecture
- infrastructure
- visual design
- spacing and layout decisions
- authentication
- security patterns
- deployment
- documentation
- testing approaches
- project structure
- recurring implementation decisions

Many of these problems have already been solved, rejected or explored in
previous projects.

Steve 2.0 should preserve useful precedent and selectively apply it to new
work.

The target is not universal reuse.

The target is **relevant inherited progress**.

A future project may therefore begin effectively 30%, 40% or more along its
journey because previously earned knowledge and capability are available at
the point of need.

---

# 3. Proposed Operating Model

The emerging system consists of several cooperating layers.

## Steve

Steve remains the owner and final authority.

The system should progressively reduce the number of low-value decisions
that require Steve's direct attention while preserving escalation for
consequential decisions and subjective judgement.

## Project OS

Project OS controls the project journey.

Its responsibilities may include:

- intake
- project state
- living project brief
- decisions
- evidence
- guardrails
- scope
- horizons
- stops
- escalation
- learning
- progression

Project OS should provide capable agents with significant freedom inside
known boundaries while being conservative about silently changing those
boundaries.

## Eolas

Eolas is the proposed organisational memory and precedent layer.

Its purpose is not to inject complete historical repositories into every
task.

It should retrieve relevant knowledge such as:

- previous decisions
- reusable patterns
- successful approaches
- failed approaches
- rejected designs
- architecture precedent
- security precedent
- infrastructure precedent
- product lessons
- previous experiments

Retrieval should be selective and proportionate.

## Steve 2.0 Build Profile

The Build Profile represents recurring preferences, defaults and established
working patterns.

It must distinguish between:

- preference
- default
- guardrail
- decision trigger
- evidence requirement

A decision made once in one project should not automatically become a
universal rule.

Repeated evidence may justify stronger precedent.

## Council

The Council provides challenge, specialist perspective and escalation.

It should not operate as a mandatory committee for routine work.

Council participation should be determined by consequence.

Relevant perspectives may include:

- Product
- Architecture
- Security
- Privacy
- Governance
- Design
- Testing
- Infrastructure
- Legal
- Marketing
- Operations

Only perspectives capable of materially changing the current decision should
normally be invoked.

## Skills and Workforce

Specialist capabilities should be loaded when required rather than placed
permanently into every project context.

Potential capabilities include:

- Product
- Research
- Design
- Development
- Architecture
- Testing
- Security
- Governance
- Privacy
- Infrastructure
- Legal
- Marketing
- Operations
- Data

Execution engines such as coding agents and models remain interchangeable.

Project OS should direct them rather than become tightly coupled to a single
agent or model.

# 4. Context and Cost

Context is a finite resource.

Project OS should avoid the common pattern of providing an agent with an
entire repository, large instruction set and complete project history when a
small amount of targeted context is sufficient.

The intended flow is:

Task
→ determine required knowledge
→ retrieve relevant current state
→ retrieve relevant precedent
→ apply relevant guardrails
→ execute

Not:

Task
→ load everything known
→ execute

Cost should eventually include more than AI tokens.

Relevant costs include:

- model/token cost
- context consumption
- Steve's time
- development complexity
- infrastructure
- hosting
- databases
- domains
- APIs
- third-party services
- support
- maintenance
- opportunity cost

The preferred decision is the cheapest sufficient approach that satisfies
the actual project need and risk.

---

# 5. Full Product Lifecycle

Project OS should ultimately operate across more than software development.

The lifecycle may include:

1. Opportunity
2. Intake
3. Product definition
4. Design
5. Architecture
6. Build
7. Test
8. Release
9. Operate
10. Learn
11. Grow
12. Retire

Projects should be able to enter this lifecycle at different points.

An inherited production system does not need to pretend it is a greenfield
idea.

An old Steve project does not need its complete history reconstructed before
useful work can continue.

---

# 6. Project Posture

Governance should be proportional to maturity and consequence.

An emerging posture model is:

| Posture | Typical State | Expected Control |
| --- | --- | --- |
| Explore | Question or opportunity | Minimal |
| Prototype | Working concept | Light |
| MVP | Real usable product | Moderate |
| Pilot | Controlled external use | Increasing |
| Production | Dependable live service | Strong |
| Commercial | Paying customers / contracts | Strong business and technical controls |
| Critical | Material dependency or sensitive impact | Highest |

This model is currently a hypothesis.

It has not been validated by Project OS experiments.

---

# 7. Stops and Decision Boundaries

Project OS should not attempt to approve every implementation detail.

Routine work inside established boundaries should proceed.

A stop should occur when work crosses a consequential boundary.

Potential examples include:

- introducing authentication
- introducing personal data
- becoming multi-tenant
- accepting payments
- creating a production deployment
- selecting or changing hosting
- registering or changing domains
- introducing material third-party integrations
- materially changing architecture
- changing a locked product decision
- introducing meaningful recurring cost
- creating commercial obligations
- materially increasing operational responsibility

A stop does not necessarily require Steve.

Possible outcomes include:

- automatically proceed using established precedent
- invoke a relevant skill
- request Council challenge
- request additional evidence
- escalate to Steve
- reject the change
- defer the idea
- stop the project

This behaviour remains largely hypothetical.

---

# 8. Completion and Value

Project OS should help create prototypes quickly.

It should also help promising work move beyond prototype and MVP.

A recurring risk is continuing to expand functionality without resolving the
small number of issues preventing a project from becoming genuinely usable,
valuable or production-ready.

Future Project OS behaviour may therefore need to protect the current
project horizon.

A useful new idea should not automatically interrupt completion of a more
valuable current objective.

The intended response may sometimes be:

**Good idea. Capture it. Not now.**

Project OS should also help identify:

- why users do not adopt something
- whether functionality is missing
- whether the product is overcomplicated
- whether the original problem exists
- whether the solution is solving the wrong problem
- whether a small utility contains a wider opportunity
- whether a capability can be packaged or reused elsewhere

---

# 9. Documentation as System State

Documentation should remain an authoritative part of Project OS.

Material changes should eventually trigger a documentation impact check.

Potential triggers include:

- completed experiment
- material decision
- changed project direction
- changed architecture
- new evidence
- changed project posture
- production release
- new operational dependency

Documentation updates should remain proportionate.

Routine implementation changes should not cause unnecessary documentation
activity.

---

# 10. External Portfolio Automation

Automatic maintenance of 1zero9.com has been identified as a useful future
project.

It should remain separate from Project OS.

A future integration could allow Project OS or Eolas to expose explicitly
approved public project metadata to the portfolio site.

Project OS may know about private projects, failures, security findings,
commercial ideas and internal evidence.

None of this should become public automatically.

Any future integration therefore requires an explicit publication boundary.

---

# 11. Evidence From Experiment 001

Experiment 001 — LaunchCity — provides evidence that Project OS can operate
against a greenfield project.

Observed value included:

- controlling assumptions
- preserving decisions
- managing frozen horizons
- identifying implementation drift
- creating useful evidence

Observed limitations included:

- evidence can be misinterpreted
- process activity does not guarantee decision quality
- unnecessary work can still occur

The experiment supports continued development of the hypothesis but does not
validate the broader Steve 2.0 model.

---

# 12. Evidence From Experiment 002

Experiment 002 — Lastman — provides evidence that Project OS can be
introduced into an independently developed active project without requiring
complete historical reconstruction.

Observed value included:

- sufficient current-state understanding
- preservation of inherited decisions
- discovery of an implicit product-direction change
- use of owner evidence when repository evidence could not establish intent
- conversion of implicit direction into a provisional explicit decision
- tracing that decision to its material security consequence
- identification of a demonstrated authorisation defect
- proportionate remediation

Observed friction included:

- a seam between existing-project adoption and v0.1's prescribed
  project-local `PROJECT-OS.md` artefact

The corrective action was statically verified rather than demonstrated
through a live breakglass session.

---

# 13. What Has Been Demonstrated

Evidence currently supports the claim that Project OS can:

- improve framing of consequential decisions
- constrain unnecessary scope
- work with both greenfield and existing projects
- preserve inherited project decisions
- use evidence proportionately
- stop unnecessary historical reconstruction
- connect product direction to material risk
- constrain remediation after a demonstrated problem

These are promising signals.

They are not proof of a complete operating system.

---

# 14. What Is Emerging

The following patterns appear promising but require further evidence:

- decision boundaries may be more valuable than rigid process phases
- stopping behaviour may be a major differentiator
- project history can be selectively retrieved rather than reconstructed
- project divergence can reveal strategic decisions rather than merely
  documentation debt
- consequence should determine which specialist perspectives are invoked
- Project OS may reduce repeated zero-to-project work
- previous projects may provide meaningful reusable precedent

---

# 15. What Remains Hypothesis

The following have not yet been demonstrated:

- Steve 2.0 as a complete operating model
- Eolas as effective cross-project memory
- automatic precedent retrieval
- Build Profile generation
- automatic Project OS injection into repositories
- automatic guardrail activation
- Council routing
- specialist workforce orchestration
- context budgeting
- token optimisation
- cost-aware model selection
- inherited progress measurement
- improved prototype-to-production conversion
- opportunity discovery
- commercial opportunity evaluation
- lifecycle governance from idea through retirement
- autonomous documentation maintenance
- portfolio automation

These should not be treated as established Project OS capability.

---

# 16. Current Assessment

Project OS remains an early but promising framework.

Two experiments provide meaningful evidence that its decision, evidence,
scope and stopping behaviours can improve real project work.

The larger Steve 2.0 vision remains substantially unbuilt and unvalidated.

The appropriate next step is not to implement the entire vision.

Future work should identify the smallest pieces that provide evidence about
whether the compounding model works in practice.

---

# 17. Framework Status

Project OS v0.1 remains:

**FROZEN**

This checkpoint records strategic learning.

It does not alter the framework.

Any future v0.2 proposal should be evaluated against both experiment evidence
and the direction recorded here.
