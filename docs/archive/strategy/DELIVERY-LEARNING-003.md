> "Horizon locally is broken. We have been doing this for two days and
> still can't get this fairly simple site working. If I was doing this

## Reproducibility failure

The Prompt 021 report relied on:

- an isolated temporary local seed;
- a never-committed seeding script;
- screenshots generated under that temporary state.

The founder's normal local application — run from the committed
repository, without that temporary seed — did not reproduce the reported
visual result.

Resulting principle:

> A proof is not complete unless the founder can reproduce and inspect it
> from the committed repository using documented commands.
>
> Screenshots generated by the delivery agent are supporting evidence, not
> acceptance evidence.

---

## Verification failure

Automated tests, builds, screenshots and an agent-run browser walkthrough
all passed while the founder-facing result was visibly broken.

The Prompt 021 agent report had claimed:

- Panel C was inspected visually;
- desktop and mobile implementations were completed;
- a real browser walkthrough was performed;
- two defects were found and corrected;
- the local review server was running with an imagery-seeded snapshot;
- the result was ready for founder visual review.

The founder's actual browser result contradicts the practical completion
implied by that report.

Conclusion:

- Technical validation did not validate the actual hand-off.
- The same agent implemented, selected test conditions, captured evidence
  and reported success.
- The founder remained the first independent user of the deliverable.
- Founder acceptance happened too late.

## Process outcome

- Project OS acted primarily as documentation and retrospective learning.
- It did not behave as an effective project lead.
- It did not reduce delivery time.
- It did not prevent repeated evidence and direction failures.
- It generated substantial prompt and documentation overhead.
- Safe deployment controls were useful, but insufficient to justify the
  overall process cost.
- LaunchCity improved technically in production, but the intended visual
  product remained incomplete.

---

## Root causes

Minimum supported root causes:

1. Too much work was initiated before founder intent and source artefacts
   were secured.
2. Agents were allowed to validate and grade their own outputs.
3. Temporary or staged states were treated as completed proofs.
4. Prompt requirements became long substitutes for direct collaboration.
5. Product review occurred after implementation rather than during it.
6. Project OS measured evidence production more readily than user-visible
   completion.
7. The process continued after multiple rework signals instead of
   triggering a hard stop.

---

## Proposed v0.2 controls

Candidates only, not promoted:

### Reproducible hand-off gate

A task cannot be described as complete unless the founder can reproduce it
from the committed repository.

### Founder-visible proof gate

For visual work, the founder must see the actual result before further
documentation, deployment or decision-status advancement.

### Independent acceptance

The implementation agent cannot be the sole acceptance tester.

### Rework stop trigger

Two consecutive corrective prompts trigger a pause and founder review
before more work.

### Delivery budget

Before starting, record an expected direct-delivery duration. If the
Project OS process exceeds that budget without visible value, pause and
reassess.

### Minimum process

Use the smallest control set proportional to the project. A small site
should not require enterprise-scale governance.

### Definition of tangible value

Count only:

- a founder-visible working result;
- a user-visible production improvement;
- or work conclusively avoided before implementation.

Documentation, tests and investigations are supporting work, not tangible
value by themselves.
