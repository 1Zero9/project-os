# Experiment 009 — Minimum v0.2 Delivery Loop Pilot

**Status:** Phase 1 complete — early structural-proof evidence recorded; Phase
2 prospective delivery validation not yet started.

## Question

Can the compact [Delivery Brief and Proof-and-Stop Gate](../../candidates/V02-DELIVERY-BRIEF-AND-PROOF-GATE.md)
produce an accepted, founder-visible result on an unrelated project with less
overhead and fewer corrective interventions than ordinary direct AI-assisted
delivery?

## Selection criteria

Choose one project that is unrelated to LaunchCity, founder-owned, bounded,
and has a clear user-visible outcome. It must have a real decision authority
and route to review, enough visual or behavioural substance for a structural
proof, no production-critical dependency, and an honest direct-delivery
comparison available. Do not select a project merely because prior Project OS
knowledge is unusually strong for it.

## Boundary

- Founder input: one initial brief/source set and one structural-proof review.
- Agent autonomy: research the cheapest material uncertainty, write the brief,
  create the proof, then implement only the founder-confirmed boundary.
- Delegation: no council by default; one independent reproducibility review is
  permitted only if it can assess committed state independently.
- Budget: maximum 90 minutes wall-clock or a founder-agreed lower cost ceiling;
  one correction cycle after structural-proof feedback.
- No deployment, paid service, or material scope expansion without separate
  founder authorisation.

## Procedure

1. Record the Delivery Brief before material implementation.
2. Build the smallest committed structural proof.
3. Obtain the founder's accept / revise / stop decision.
4. If accepted, implement only that boundary and run the Proof-and-Stop Gate.
5. On a second unaccepted correction, missing authority, non-reproducible proof,
   or budget overrun without accepted value: stop and rebaseline.
6. Record only the outcome data below and one reusable learning, if material.

## Measures

| Measure | Why it matters |
|---|---|
| Time to founder-visible structural proof | Whether the loop reaches the important decision early |
| Founder interventions | Whether autonomy is real rather than hidden hand-holding |
| Accepted user-visible result | Primary delivery outcome |
| Rework avoided / caused | Whether the gate prevents or creates waste |
| Wall-clock time and observable delivery cost | Comparison with direct delivery |
| Committed-state reproducibility | Whether hand-off evidence is real |

Prompt count, documentation volume, commit count, and passing technical checks
are supporting diagnostics, not success measures.

## Classification

**SUPPORTED** only if the founder accepts the result within budget, it
reproduces from committed state, and the process is plausibly no slower or more
burdensome than direct delivery for the same scope.

**PARTIALLY SUPPORTED** if the proof/gate prevents material wasted work but the
accepted result, budget, or direct-delivery comparison is mixed.

**NOT SUPPORTED** if the loop creates material overhead without preventing
rework, cannot reach acceptance, or direct delivery would clearly have been
faster and better.

## Guard against hindsight

Freeze the selected project, founder source material, brief, budget, and
classification criteria before the structural proof begins. Do not add a
candidate control during the pilot to rescue its result.

## Phase 1 — Early structural-proof case

Vecta was used for a bounded early case after the founder supplied a direction
for it to act as a quiet, sensible guide to a new job. It reached a committed,
founder-visible structural proof using existing state, then stopped when the
founder explicitly returned priority to Project OS. The case is recorded in
[`docs/evidence/009-evidence-log.md`](../evidence/009-evidence-log.md).

This is deliberately not classified as SUPPORTED, PARTIALLY SUPPORTED, or NOT
SUPPORTED: it did not test an accepted finished outcome, direct-delivery
comparison, or the full pilot boundary.

## Phase 2 — Prospective delivery validation

The next section of Experiment 009 is one fresh, bounded founder-owned piece
of work. Before implementation, freeze its Delivery Brief, budget, acceptance
evidence and classification criteria. Run the full procedure above through an
accepted outcome or a stop condition.

The founder's 80% idea-to-project ambition remains a long-term aspiration for
weeks/months of demonstrated progress. Phase 2 does not attempt to prove it;
it tests only whether the compact loop creates an earlier, better delivery
decision than direct work.
