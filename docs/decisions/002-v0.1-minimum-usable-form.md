# Project OS v0.1 — Minimum Usable Form

## Status

- **Version:** v0.1 experiment
- **Based on:** ADR 001 — Project OS v0.1 Promotions
- **Purpose:** Define the smallest usable representation of the five promoted capabilities
- **Constraint:** Manual first. No agents, orchestration, CLI, scoring engine or automation.

---

## 1. Decision

Project OS v0.1 will initially be implemented as **one small project-local control file**:

```text
PROJECT-OS.md
```

This file is created in the root of the project being tested.

It contains five sections corresponding to the five promoted capabilities:

1. Project Intake
2. Relevant Knowledge Check
3. Risk & Failure Check
4. Scope & Stop Check
5. Learning Capture

This is deliberately smaller than creating five separate files, agents or workflows.

The first experiment needs to prove that the capabilities are useful before Project OS invests in machinery around them.

---

## 2. Why one file

The archaeology repeatedly warned against premature structure.

Five capabilities do not require five subsystems.

A single file gives us:

- one obvious place to look;
- low setup cost;
- visible project state;
- easy use by a human or coding agent;
- straightforward Git history;
- no new tooling;
- no hidden automation;
- easy deletion if the experiment fails.

If `PROJECT-OS.md` becomes too large or serves conflicting purposes during real use, that will be evidence for splitting it later.

We should not predict that problem in advance.

---

# 3. Operating rule

`PROJECT-OS.md` is not a project specification.

It is a **decision-support record**.

It should contain only information that helps Project OS:

- understand the project;
- reuse previous knowledge;
- challenge meaningful risks;
- detect drift;
- retain useful learning.

Detailed product requirements, architecture, roadmap and implementation documentation remain in normal project files where appropriate.

---

# 4. Activation model

The five capabilities are not a mandatory sequence.

## Project Intake

Run at the start of a new project or when Project OS first encounters an existing project.

## Relevant Knowledge Check

Run before a significant decision when previous experience may be useful.

## Risk & Failure Check

Run before implementing or releasing something where failure has meaningful consequence.

## Scope & Stop Check

Run when:

- scope grows;
- repeated iterations occur;
- architecture is being reworked;
- working software is being replaced;
- methodology begins expanding;
- the project feels stuck;
- a release decision is approaching.

It may also be invoked explicitly at any time.

## Learning Capture

Run when something happens that could materially improve a future project.

Do not run it merely because work occurred.

# 6. Process depth

v0.1 will use only three descriptive levels:

- **Light**
- **Standard**
- **Deep**

These are not scores.

There is no formula.

## Light

Use when the project is:

- low consequence;
- easy to reverse;
- well understood;
- small in scope;
- exploratory.

Example behaviour:

- short intake;
- knowledge check only where obviously useful;
- risk check focused on obvious failure;
- minimal learning capture.

## Standard

Use when there are meaningful:

- users;
- dependencies;
- production consequences;
- architectural choices;
- data concerns;
- ongoing maintenance.

## Deep

Use when failure could materially affect:

- security;
- privacy;
- governance;
- money;
- operations;
- organisational trust;
- difficult-to-reverse architecture;
- multiple stakeholder groups.

### Important

These levels describe how much attention to apply.

They do not activate predetermined documents or ceremonies.

If the three levels prove too vague, that becomes evidence for refinement.

Do not create a scoring system yet.

---

# 7. How an AI coding agent should use it

A coding agent working in a Project OS-enabled repository should be told:

> Read `PROJECT-OS.md` before making significant product, architecture or restructuring decisions. Treat it as decision context, not as a replacement for project requirements. Update it only when a Project OS checkpoint produces a material decision or reusable learning. Do not expand the file with routine implementation detail.

That is enough for v0.1.

We do not yet need provider-specific agent systems.

---

# 8. Minimal checkpoint prompts

The experiment can initially be operated with five short prompts.

## Intake

> Review this project using the Project Intake section of `PROJECT-OS.md`. Establish only the context that could materially change how we approach the project. Recommend Light, Standard or Deep process depth and explain why. Do not design the solution yet.

## Relevant Knowledge

> Before we make this decision, check our existing Project OS archaeology, decisions and project knowledge for relevant prior learning. Return only evidence that could materially affect this decision. State whether to use, adapt or ignore it.

## Risk & Failure

> Run a proportionate Risk & Failure Check on the current decision or implementation. Focus on realistic negative paths, partial failure, recovery, lifecycle and external dependencies. Do not create a generic risk register.

## Scope & Stop

> Run the Project OS Scope & Stop Check. Compare current activity with the original objective. Identify scope accumulation, repeated iteration, unnecessary abstraction, changes to working software and diminishing returns. End with one decision: Continue, Freeze, Ship, Re-scope or Stop.

## Learning Capture

> Review what just happened and decide whether anything is worth retaining for future projects. Capture only learning that could materially improve a future decision. If there is nothing worth retaining, say so and do not create a record.

# 9. Relevant knowledge in v0.1

There is no Eolas system yet.

For the first experiment, relevant knowledge comes from the repository's existing evidence:

```text
PRODUCT-OS-ORIGIN.md
PRINCIPLES.md
ROADMAP.md

docs/
├── archaeology/
└── decisions/
```

If the test project has its own previous decisions or documentation, those are also valid sources.

Retrieval can be manual or performed by the AI environment already working with the repository.

The objective is to test whether **retrieving previous judgement is useful**, not whether we can build a sophisticated retrieval engine.

---

# 10. Learning records in v0.1

Do not immediately move every Learning entry into a central knowledge system.

During the experiment, leave the learning in the test project's `PROJECT-OS.md`.

After the project or a meaningful milestone, review the accumulated learning.

Only then ask:

> Which of these deserves promotion into Project OS knowledge?

This gives us a natural evidence pipeline:

```text
PROJECT EVENT
      ↓
LOCAL LEARNING
      ↓
REPEATED / MATERIAL?
      ↓
REVIEW
      ↓
PROMOTE or LEAVE LOCAL
```

This protects Eolas from becoming a dumping ground.

# 11. What we are deliberately not building

v0.1 does not need:

```text

playbooks/

```

It also does not need separate files such as:

```text

RISKS.md
BRAKE.md
LEARNING.md
```

unless real use demonstrates that one-file operation is inadequate.

# 12. Experiment telemetry

We need enough evidence to judge Project OS itself.

At the bottom of the test project's `PROJECT-OS.md`, add:

```markdown
## Project OS Experiment Log

| Date | Capability | Why invoked | Material change? | Friction | Notes |
|---|---|---|---|---|---|
```

Do not log token counts, prompt counts or detailed AI analytics yet.

For v0.1 we need to know:

- Did the capability change anything?
- Was that change useful?
- How annoying was the process?

That is enough.

---

# 13. Evaluation questions

After a meaningful period of real use, review the experiment.

## Value

- Did Intake prevent premature work?
- Did Relevant Knowledge retrieve anything genuinely useful?
- Did Risk & Failure identify something we would otherwise have missed?
- Did Scope & Stop prevent wasted iteration or scope?
- Did Learning Capture preserve anything worth reusing?

## Cost

- Which capability felt bureaucratic?
- Which produced generic advice?
- Which duplicated normal development work?
- Which required too much maintenance?
- Which was repeatedly skipped?

## Architecture

- Did one `PROJECT-OS.md` remain usable?
- Did any section need independent lifecycle or ownership?
- Did any capability clearly justify automation?
- Did any capability clearly justify becoming a skill or agent?

---

# 14. Promotion rule after the experiment

Do not expand Project OS because a feature seems convenient.

A v0.1 capability may gain more machinery only when real use demonstrates one of the following:

1. manual repetition creates meaningful friction;
2. important checks are repeatedly forgotten;
3. the single-file model becomes genuinely difficult to use;
4. retrieval fails because the evidence volume is too large;
5. a specialist role repeatedly changes decisions;
6. automation would remove demonstrated work without hiding judgement.

Otherwise, keep the primitive implementation.

---

# 15. Recommended first test

The first test should be a **real project that is about to move forward**, not a synthetic Project OS demo.

It should ideally have:

- a genuine objective;
- enough uncertainty for Intake to matter;
- at least one meaningful decision;
- some opportunity to reuse previous knowledge;
- low enough consequence that v0.1 itself does not create risk.

Avoid selecting a project merely because it will exercise all five capabilities.

Project OS should adapt to the project, not choose a project to flatter Project OS.

---

# 16. Brake applied to this decision

Could we create a richer implementation now?

Yes.

Would the archaeology justify it?

No.

The minimum testable hypothesis is:

> **A single concise project-local file, used at meaningful decision points, can provide enough structure to improve AI-assisted project work without becoming another framework.**

That is what v0.1 should test.
