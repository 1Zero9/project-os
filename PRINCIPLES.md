# Project OS — Principles

These principles govern how Project OS is developed and applied.

They are derived from project archaeology, experiments and observed project
work rather than speculative framework design.

Principles should change slowly.

A new principle requires evidence. Existing principles should only be changed
when subsequent evidence demonstrates that they are incomplete, harmful or
incorrect.

---

## 1. Evidence Before Framework

Do not add something to Project OS because it appears useful in theory.

Add or change framework capability when project work, archaeology or controlled
experimentation demonstrates why it should exist.

Ideas without sufficient evidence belong in the roadmap.

Framework friction encountered during an experiment is evidence to record,
not permission to silently change the framework.

---

## 2. Current State Before Reconstructed History

Understand enough of a project to make the next meaningful decision.

Do not reconstruct complete project history, documentation or rationale unless
the missing history is materially necessary to the decision being made.

Existing code, documentation, implementation state and owner evidence may be
sufficient.

Historical investigation should be targeted.

---

## 3. Consequence Determines Depth

Apply effort in proportion to the consequence of the decision.

Routine and reversible decisions should not receive the same analysis,
challenge or evidence burden as decisions involving significant:

- security risk
- privacy impact
- architecture change
- scope change
- cost
- operational responsibility
- irreversible work
- product direction

Use the cheapest sufficient level of investigation and intelligence capable of
supporting the decision.

---

## 4. Stop Work as Readily as Start It

Project OS exists to subtract unnecessary work as well as direct useful work.

Valid outcomes include:

- proceed
- defer
- reduce scope
- preserve the current decision
- investigate further
- capture an idea for later
- reject
- stop

More activity is not inherently progress.

---

## 5. Preserve Decisions Until Evidence Warrants Reopening Them

Established project decisions should be inherited rather than repeatedly
relitigated.

A previous decision may be reopened when new evidence, changed circumstances
or material consequences justify doing so.

Preference or curiosity alone is insufficient.

This preserves momentum while allowing projects to adapt when reality changes.

---

## 6. Fix the Demonstrated Problem

When evidence demonstrates a specific problem, correct that problem
proportionately.

Do not automatically expand a targeted intervention into adjacent redesign,
refactoring, feature development or speculative remediation.

Adjacent concerns may be recorded and investigated separately when warranted.

Asked-for work does not automatically authorise neighbouring work.

---

## 7. Documentation Serves Decisions

Documentation is a means of preserving intent, evidence, decisions and useful
project state.

Creating documentation is not itself evidence of progress.

Documentation should be:

- proportionate
- current where materially necessary
- authoritative where decisions depend on it
- updated when material state changes
- avoided when it exists only to satisfy process

The purpose of an artefact is to improve future understanding or decisions.

---

## 8. Framework Friction Is Evidence

Project OS should be tested as it exists.

When an experiment exposes ambiguity, unnecessary process, missing capability
or conflict with real project work, record the friction.

Do not repair the framework during a controlled experiment unless the
experiment explicitly permits it.

This prevents Project OS from appearing successful only because it is changed
whenever reality challenges it.

---

## 9. Project OS Must Earn Its Cost

Project OS introduces its own cost:

- time
- context
- tokens
- documentation
- review
- interruption
- cognitive overhead

That cost must be justified by improved decisions, avoided work, reduced risk,
greater reuse or faster delivery of value.

If Project OS creates more process than value, Project OS is the problem.

---
